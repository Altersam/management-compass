## 1. Продукт и подтверждённая исходная линия

Есть два входа, четыре этапа, десять тем, тридцать техник, тридцать микровопросов, пятьдесят вопросов, десять справочных кейсов. Курс начинает с ситуации. Справочник хранит развёрнутые объяснения, рабочие шаблоны, избранное и дневник. Отдельно работают Адизес, литература, профили, резервные копии и эксперименты.

Проверено до изменения приложения:

- `npm test`: 34/34 успешны.
- `npm run test:browser`: 16/16 успешны, Chromium, локальный сервер, Windows.
- `npm run build`: успешна.
- Команд `lint:content` и `test:a11y` пока нет. Это пробел исходной версии, не результат проверки.
- Браузерные сценарии уже проверяют все фазы тем при 390 px, несколько клавиатурных действий, reduced motion, старые данные, импорт, справочные формы и схемы.

## 3. Дубли и legacy

Воспроизводимый инвентаризатор: `node scripts/content-audit.cjs`. Он только читает исходные данные. Точные совпадения — кандидаты на анализ, не повод удалять текст.

- `knowledge.js` дописывает intro, три details, terms и третью технику к каждому chapter; повторное выполнение добавит ещё одну технику.
- `course-data.js` задаёт blockTitles из справочника; `learning-content.js:62–64` заменяет их учебными заголовками и дублирует bridge в module.next.
- `question-revision.js` меняет формулировки через `(answer + sourceIndex) % 3`: для исправления альтернативы приходится знать прежний порядок. Канонический индекс нельзя менять при переносе.
- `case-revision.js` заменяет три параллельных массива options/appeals/feedback. В schema их нужно нормализовать, а legacy view получать адаптером.
- `course-questions.js` создаёт `finalQuestions` из существующих вопросов. После revisions часть analysis совпадает с банком, а формулировки старого итога отличаются. Новый UI использует SimulationEngine; legacy finalResults и finalQuestions пока сохраняются для совместимости и проверки переноса.
- Точные повторения: краткие descriptions в connections; bridge в module.next и pedagogy; analysis в legacy finalQuestions. Пример: «Ни ресурс, ни право выбора у участников не изменились — решение снова зависнет» встречается в `m6-q3` и старом финале.
- Смысловые пересечения: темы 2/6 — эскалация; 2/7 — результат и статус; 5/7 — получение/понимание; 8/10 — защитная метрика; 9/7 — объявление и применение. Нужны разные контексты и retrieval, а не повтор одного универсального рецепта.
- Универсальная appeal микровопросов («Этот вариант опирается на одну из видимых сторон ситуации») повторяется 90 раз. Заменять при содержательной ревизии конкретным основанием.
- Правильные позиции в 50 вопросах: 17/17/16; верный ответ строго длиннее остальных в 14/50. Уже нет систематической подсказки первым/самым длинным ответом; lint должен удерживать это свойство.
- Современные microAnswers/activities и прежние visited/diagnostic/practice/attempts сосуществуют. Это необходимая совместимость, а не мусор.

## 5. Данные и migration plan

Не меняем ключ `management-compass:v1`, envelope `{version:1,active,profiles}` и формат export `management-compass-profile`, version 1. Внутри данных вводим `dataVersion:3`. Миграция чистая, повторяемая и добавляющая: никаких переиндексаций вариантов и удалений legacy.

Сохраняемые namespaces:

Обнаруженные риски:

1. `store.validateData()` собирает верхний уровень, journal и experiments по whitelist и теряет неизвестные поля при импорте. Перед добавлением observations/nextExperiment исправить lossless round-trip, сохранив проверки обязательных полей и недопустимых ключей.
2. `load()` возвращает старые данные без defaults. Старый profile может не иметь course/experiments; миграция должна одинаково применяться при загрузке и импорте.
3. Новая симуляция не должна replay старые строки по новому графу. Revision 2 хранится и воспроизводится отдельно; новый путь revision 3 использует scene/action IDs и новую запись.
4. Завершение старого курса нельзя отозвать из-за новых упражнений. `legacyCompleted` и ранее заработанное освоение сохраняются.
5. Cache при quota failure уже защищает свежие заметки; миграция не должна повторно читать старое хранилище и терять их.
6. Профиль по query `user` отличается от active в envelope; все новые формы и переходы должны использовать фактически открытый профиль.

## 6. Архитектурный переход

Целевой поток: `page entry → services + topic loader → topic object → activity/UI`; зависимости выражены import/export. Никакого runtime скачивания статьи, внешних библиотек или личных данных.

- `content/topics/01-self-management.js` … `10-data.js`: единица авторского редактирования темы. Объект включает concepts, misconceptions, scene, explanations, activity, techniques, cases, questions, retrievalQuestions, navigatorSignals, requiredBehavior, incentives, informalActors, functionNeeds, simulationHooks, references, bridge.
- `content/topic-schema.js`: контракт и проверки; `content/topics/index.js`: explicit dynamic-import map, без импорта всех тем на главной.
- `assets/pages/*.js`: отдельные entry для главной, урока, рабочего режима, справочной темы и дополнительных страниц.
- `assets/activities/*.js`: контракт mount/getState/evaluate/renderFeedback и cleanup; разделить ten-topic switch по одной механике.
- `assets/core/`: storage/migrations, profile links, choices, course progress. Чистые вычисления импортируются тестами без DOM.
- Simulation и вопросы грузятся по требованию. Для продолжения на главной достаточно saved state и небольшого каталога названий.
- Временные compatibility adapters явно документируются; они не являются вторым местом авторской правки. Удалять слой только после проверки equivalence исходного итогового контента и адаптеров.
- Сервер/сборка должны одинаково поддерживать вложенные content/assets и только публичные расширения; запрещены traversal, symlinks и непубличные материалы.
- Перевести VM-тесты с parsing классического JS на module import и проверку links/import graph; browser tests проверяют UI/данные, а не наличие globals.

## 7. Статья: идеи и ограничения переноса

Прочитан приложенный PDF: основной текст на страницах 1–19; дальше реклама/служебные блоки сайта. Используются собственные обезличенные сцены и объяснения.

Используем: повышение меняет требования работы (стр. 2); формальная схема не отражает все зависимости (2–4); система нуждается в разных функциях (5–9); предпочтения взаимодействия важны для порядка аргументов (12–13); повторяемое поведение руководителя масштабируется (15); стимулы делают обход рациональным (16–18).

Не переносим: буквальную матрицу PAEI/DISC/social styles (14–15), утверждения о неизбежном саботаже сочетаний «типов» (12), подбор/смену руководителей по типологии (18), обещание универсального эффекта или нулевой стоимости. PAEI — функции системы, DISC — наблюдаемая манера действий, социальные стили — линза взаимодействия в контексте. Никакого теста личности или конвертера между моделями.

## 8. Очерёдность и критерии приёмки

1. Аудит и исходные проверки (этот документ).
2. Schema, модульные entry, миграции и content lint, сохраняя UX. Проверить equivalence и отсутствие eager bank/simulation на главной.
3. Тема 3 и team builder; затем тема 5; тема 6 и карта команды; тема 9 и canvas.
4. Гипотезы навигатора и новые ситуации.
5. Ветвящаяся симуляция, delayed effects, «тень» и сравнение путей.
6. Taxonomy, retrieval/interleaving и продуктивные ответы.
7. Эксперименты, документация, accessibility и полировка.

После этапа: Node tests, browser tests, content lint (после его введения), build, diff check; отдельный содержательный commit. Финальный контент нельзя оценивать только количеством объектов: новые параметры должны менять причинный результат.

Lint: уникальность IDs, валидность ссылок, completeness feedback, taxonomy, simulation actions, длина/позиции ответа, служебные шаблоны, личностные ярлыки. Точные и близкие повторы — отчёт для редактора, не автоматическое удаление.

A11y: axe и ручной клавиатурный путь целой темы, labels/fieldset/legend, focus после смены экрана, объявления результатов, ranges, reduced motion, 320/375/430/768/1024 px без document overflow. CI блокирует artifact/deploy при неуспешном lint/test/a11y/build.

## 9. Открытые технические вопросы

- Сначала подтвердить compatibility адаптером, затем переносить авторские данные тем: большой одномоментный перенос труднее проверить.
- Порог похожести предложений следует калибровать на отчёте: совпадение термина не означает дублирование объяснения.
- Retrieval должен работать локально по датам и прошлым действиям, а не требовать непрерывного посещения или сетевого сервиса.
- Новые simulation состояния — учебная модель, не прогноз организации; проверять направление, условия и trade-offs, а не обещать точные реальные числа.
